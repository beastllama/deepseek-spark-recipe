# 786,432-position shared KV pool

On November 17, 2026, we selected the 786,432-position pool for two DGX Sparks after it finished one five-request long-context wave 7.7% sooner. It admitted five requests where the 655,360 pool peaked at four. Interactive latency moved the other way for the short request. Both profiles use EAQ v1 with matching abliterated Keys, High reasoning, eight API lanes, 524,288 context per request, a 32,768-token output allowance, and the 1 GiB prompt snapshot store. The shared pool serves all lanes.

## Build and launch

Use the [pinned assets](README.md#external-assets), [native build instructions](README.md#build), and [existing memory and thermal protections](README.md#launch). On Linux or a Linux filesystem in WSL, start with the [November 15 shared-pool reconstruction](ADMISSION-BENCHMARK.md#reproduce-the-engine-pair) through `shared-pool-capacity.patch`. Then apply the streaming heartbeat patch and verify the production source closure.

```sh
git -C tensorfold apply --check ../patches/sse-heartbeat.patch
git -C tensorfold apply ../patches/sse-heartbeat.patch
python3 scripts/verify-source.py tensorfold --manifest data/source-manifest-sse-heartbeat.json
```

Build that verified tree and use `ADMISSION_PROFILE=shared-pool-768` in both ranks’ operator-owned [runtime files](config/runtime.env.example). The launch adapter sets `TF_DS_POOL_TOKENS=786432` on the head and `--pool 786432` on the worker. Both keep `--context 524288`. Keep the 655,360 option by selecting `ADMISSION_PROFILE=shared-pool` on both ranks. Drain work, stop both ranks through your normal controls, and verify both have stopped before switching profiles. Confirm the head reports the expected `pool_tokens` and both ranks are ready before admitting work. The extra positions require approximately 111.25 MiB of estimated KV payload per rank before allocator rounding and driver effects. Check available memory on both nodes.

The heartbeat checks the existing stream keepalive every 25 seconds, including while model rounds produce no visible SSE data. It reuses OpenAI chat comments and Messages pings, and a failed write cancels through the existing request path. The Responses endpoint lacks a ping callback on this source. Two focused regressions reproduced the failure before the patch and passed afterward. The selected build recovered all 16 keys in one 128K SparkDash recall, with zero stale keys or observed disconnects. That run confirms streamed completion on the selected profile. How often the patch prevents timeouts in real work remains unmeasured.

The production deployment used a rebuilt head and the retained compatible follower. The published source and local artifact hashes identify what was measured. A clean public GPU build, binary equivalence, and independent hardware qualification are pending. [Artifact and numerical evidence](data/kv-pool-786432-results.json).

```sh
git -C tensorfold apply --check ../patches/kv-pool-admission-observation.patch
git -C tensorfold apply ../patches/kv-pool-admission-observation.patch
python3 scripts/verify-source.py tensorfold --manifest data/source-manifest-kv-pool-admission-observation.json
```

Prepare the [pinned SparkDash 2.90.0 checkout](ADMISSION-BENCHMARK.md#reproduce-the-sparkdash-workload) through `sparkdash-2.90-admission-benchmark.patch`. Apply this second patch before building SparkDash.

```sh
git -C sparkdash-admission apply --check ../patches/sparkdash-2.90-kv-pool-comparison.patch
git -C sparkdash-admission apply ../patches/sparkdash-2.90-kv-pool-comparison.patch
```

The two dashboard patches apply in order at the stated pin. For a focused collector check, copy [the fixture test](tests/sparkdash/AdmissionPoolBench.test.js) to `sparkdash-admission/server/collectors/__tests__/` and run both admission test files with Node’s test runner. ## Measured tradeoffs

| Metric | 655,360 pool | 786,432 pool |
| --- | ---: | ---: |
| Five-request wave | 41.02 s | 37.86 s |
| Entire SparkDash job including cold prime | 103.75 s | 100.87 s |
| Completions/minute during wave | 7.31 | 7.92 |
| Peak sampled running requests | 4 | 5 |
| Mean native queue wait | 7.05 s | 3.68 s |
| Longest native queue wait | 27.33 s | 10.47 s |
| Short request queue wait | 4.97 s | 10.47 s |
| Mean request completion | 30.86 s | 36.03 s |
| P95 of per-request longest SSE pause | 1.128 s | 1.417 s |
| Capacity / contiguous placement refusals | 20 / 4 | 0 / 0 |
| Cached tokens across inputs | 532,480 / 548,733 | 532,480 / 548,733 |
| Generated tokens across five natural stops | 3,295 | 3,556 |
| Lowest sampled available memory, head / worker | 7.05 / 9.24 GiB | 6.65 / 8.81 GiB |

This was one paired synthetic wave with naturally varying output lengths. The larger pool admitted all five and reduced batch wall time, mean queue time, and worst queue time. The earlier capacity-blocked 8K tail waited 5.11 s instead of 27.33 s. Individual completion was slower on average, and the short request waited longer. Whole-project completion, sustained reliability, and quality beyond the narrow recall check remain unmeasured.

A later 4,304-token cached-tail timing pass measured about 1.05 s and 0.94 s for the two full chunks on the head stream. Cache restore and snapshot copy each took about 1.3 ms on that stream. The 61-token short request queued 9.72 s, including 4.26 s behind a parked prefill, with zero placement refusals. The run had a different admission order and did not reproduce the earlier contested stream gaps. The scheduler settings stayed as measured above.
